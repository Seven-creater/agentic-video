# 精看证据区间反馈修复

## 实际故障

第二条参考视频的服务器原样测试 `server_reference_7692329355342679331_20261009`
在收到29条视觉回复后停止，没有渲染成片。最终输入是原片2020–2025秒的
5秒切片；028回复的e2、e3、e4分别写成2–2、3–3、4–4秒。
029唯一修复又把全部五条证据写成零长度区间。

旧校验将 `start < end` 和上界约束合并报告为
`semantic/evidence:outside_observed_slice`。这次实际失败是起止相等，
没有超出5秒上界，也没有证据表明模型混用了原片绝对时间。
旧反馈没有说明这一差异，也只暴露第一个错误。

原始证据在任务的 `calls/glm_028_semantic_slice_0_7f3826a1e389c1bf/`
及 `calls/glm_029_semantic_slice_0_7f3826a1e389c1bf_repair/` 中。
本地完整记录为 `runs/server_reference_7692329355342679331_20261009/GLM_RUN_RECORD.md`。
这些回复和失败记录不因代码修复而改写。

## 修复范围

仅修改 `semantic_audit.py` 的失败诊断：维持原校验规则、1毫秒上界容差、
异常文本和校验顺序，在时间校验失败时附加完整的 `diagnostics`。
它列出每个无效证据的ID、数组位置、原始起止值及具体原因：
零长度、倒序、真实越界、负值或无效时间值；同时给出当前观察时长和
`0 <= start < end <= observed_duration_s` 要求。

现有 `CodexMCP` 会把这些信息写入新调用的失败记录，并传给唯一格式修复，
无需新增重试机制或更改执行流水线。诊断仅投影时间相关字段，非有限数字
转为描述字符串，保证失败记录可以严格JSON序列化。

不自动补时长、不接受点时间作为动作区间、不提供电影剧情或人工切点。
旧提示与已保存请求保持原样；修复提示中的约束来自本地校验反馈。
源切片审核与成片盲读共用这一校验器，因此两处反馈均得到修正。

## 验证与限制

离线测试覆盖028/029的区间结构、批量错误反馈、无效数值、原有容差、
局部及成片时间字段、实际队列的唯一修复、修复耗尽后不产生第三请求，
以及缓存重验时保存旧付费调用文件。既有提示字节与语义合同回归仍须通过。
这些合成测试验证协议行为，不能证明GLM能从实际视频确定动作边界。

本修复不注册第三次观察、不重放028/029、不启动新候选或渲染。
原任务仍为29条收到回复、0条成片；运行证据与结果保持不可变。
服务器发布采用独立版本和安装包检查，不向已停止任务替换控制记录。
