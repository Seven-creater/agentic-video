# INC-20261029-16 模板采集(hunter)被工作目录预算挡住:512MB 预算算进了 191MB 持久回执

| 项 | 内容 |
|---|---|
| 发现日期 | 2026-10-29 |
| 影响范围 | 服务器模板采集(hunter);运维阻塞——采集因磁盘预算不足无法进行 |
| 状态 | 已修复(服务器脚本 `bin/hunter-server` 改为每次采集用独立 `runs/<时间戳>` 目录;无 git 提交号,原文件备份 `.bak_20261029`) |
| 相关提交 | 无(服务器侧脚本,不在仓库) |
| 相关任务 | hunter 采集运行(具体 run id 未记录) |

## 1. 问题长什么样
采集任务的工作目录预算 512MB,但实际占用 844MB:持久回执 191MB + 两个配乐实验 654MB 被算进同一目录,采集未开始即超预算被挡。

## 2. 怎么查出来的
对工作目录做体积归因:844MB 总量中回执 191MB、配乐实验 654MB——两者都是应长期保留的数据,却被当作本次采集的可回收预算。

## 3. 根因
操作/脚本问题(目录职责混用):单一大目录同时承担"本次运行的工作区(有预算上限)"与"持久数据(回执防重发、历史实验)"两种职责,预算把持久数据误算为可支配空间。

## 4. 解决方案
服务器 `bin/hunter-server` 改为每次采集使用独立的 `runs/<时间戳>` 目录(每次从空目录开始,预算只约束本次);持久回执仍共享存放——刻意保留,因为回ceipt 共享是防重发机制的一部分。原文件备份 `.bak_20261029`。

## 5. 为什么不用其他方案
- 把回执也隔离进每次运行目录:会失去跨运行的防重发能力(同一视频不重复采集/计费依赖共享回执);故回执共享不动。
- 调大预算阈值:治标,目录职责仍混用,迟早再次膨胀。
- 其余备选:未讨论。

## 6. 怎么验收
修复后的采集运行在预算内完成(服务器实测;具体输出未归档)。

## 7. 量化数据
修复前:预算 512MB,实际 844MB(回执 191MB + 配乐实验 654MB,加本次采集需求),超支约 332MB。修复后单次运行目录体积未记录。

## 8. 经验与后续
- 工作区(有预算、可清)与持久数据(回执/历史)必须分目录;预算只对工作区生效。
- 改服务器脚本要留备份(本次 `.bak_20261029` 模式)。
