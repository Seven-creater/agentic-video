## 2. 怎么查出来的
对服务器任务 `e2e_20_赵德汉藏钱_10312000` 逐级看产物：`reference_reading.json` 的 `visible_evidence` 只有 3 条 → `question_first/questions.json` 恰好 3 个节拍 → `calls/glm_160_plan_0/request.json` 的提示词含"自主决定段落和片段…不必复刻参考故事结构"，上限只有"最多32个segments、不超过180秒"。再对 5 个模板统计参考时长、ASR 句数、节拍数、成片时长（上表），节拍数与 visible_evidence 条数一一相等，与参考台词量无关。

## 3. 根因
- 直接原因：`reference_beats()`（src/omni_story/library/question_first.py:574，修复前）"每条 visible_evidence 一个节拍"，QUESTIONS 提示词要求"节拍已由 visible_evidence 逐项固定…不得增加、删除、合并节拍"。visible_evidence 是"支持主旨的证据"，不是故事分镜，通常只有 2–6 条。
- 根本原因：流程里没有任何一步把参考的完整故事（段落顺序、对话来回、时长）写下来；规划提示词（src/omni_story/library/prompts.py:101）明确说不必复刻结构，只给上限不给目标时长；精剪 `do_not_lengthen_rough`（src/omni_story/library/story_finecut.py:111）再把短粗剪保持为短。属于流程设计缺口（代码问题）。

## 4. 解决方案
1. 新增分镜步骤 `src/omni_story/library/storyboard.py`：参考理解之后单独一次 GLM 调用，按时间顺序写完整分镜（每格 1.5–8 s，覆盖 ≥90%，每句 ASR 必须归到某格，格内可多人多句），程序机械校验并给可修复反馈（3880068、6c940af）。
2. 找素材节拍改由分镜生成：每格每个说话人一道题，相邻格同说话人同角色合并（跨度 ≤16 s）；非核心格无素材时并入相邻有素材的节拍（上限为格数 30%，向上取整；用户 10-31 决定）；核心格缺素材维持原策略（e186def）。
3. 规划：提示词改为"按分镜段落顺序、对话轮次和节奏组织，画面与台词可重释"；新增可修复违规：总时长须在参考 ×[0.8, 1.2]、每个核心格至少一个片段、并入格 ≤30%、台词条数 ≥ ceil(0.7×分镜有说话人的台词数)；精审逐个核心格输出 `storyboard_coverage`，未讲到即走既有 `reselect_material` 路径（deb8043）。
4. 分镜路径下角色由程序按分镜字母固定（791af39，见 INC-20261101-01）。

通用性：所有规则只依赖参考自身的时长、ASR 与分镜结构，不含任何模板、人物或台词特判；旧任务（锁里已有 question_first_cache、无 reference_storyboard）逐字节走旧路径。

## 5. 为什么不用其他方案
- 让参考理解多写几条 visible_evidence：它的语义是"主旨证据"，多写也不等于故事顺序和对话轮次，且挤占参考理解提示词。
- 只在规划提示词里加"成片接近参考时长"：没有分镜，规划只能靠拉长少数镜头凑时长，内容仍然少。
- 每格一道题不按说话人拆：一格里 A 问 B 答时只会找一个人的镜头，对话来回丢失。
- 缺素材一律停：格变多后停机率上升；用户 10-31 选择非核心格并入相邻段。
