# INC-20261116-01 目录收录了无法观看的窗口，GLM 选中后整条任务停机

| 项 | 内容 |
|---|---|
| 发现日期 | 2026-11-16 |
| 影响范围 | scene_v1 素材浏览（所有模板共用的吉伊卡哇素材库）；致命停机 |
| 状态 | 已修复，release `scene_v1_schedule_03deaebad6fb`；13 号模板留到最后补跑 |
| 相关提交 | 未提交 |
| 相关任务 | `trials/fast_template_20261115_163928_13_自己吓自己_01_f291cd257776` |

## 1. 问题长什么样
报错为 `material_browser_full_window_crosses_excluded_range:vl_d330366f68599f91`，位置在 `material_browser.py:465`。浏览第 1 轮 overview 处理到第 3 个窗口时，还没调用模型就停了。

## 2. 怎么查出来的
夜间值守先取证，再由 GLM 做只读诊断（`night_diag/13__1116_0129_glm.md`），结论经人工复核。窗口能否进入目录，由 `autonomous_material.py:58-60` 按单条索引记录判定，只要有一条记录避开排除区就收录。生成看片代理时，`proxy()` 却按整窗 17 秒重新判定，只要窗口和排除区（标题卡、片头片尾、风格化插入）有交叉就停机。

## 3. 根因
同一个窗口在目录收录和实际观看两处用了不同的判定标准：目录收录了按整窗标准无法观看的窗口。GLM 按协议正常选了它，结果没有可修复的余地（`LibraryStopped` 不经过模型修复流程）。属于流程分支不一致。

## 4. 解决方案
新增 `MaterialBrowser.window_allowed(wid)`，按整窗范围判定。`catalog_rows()` 和 `proxy()` 都改用它，横跨排除区的窗口从一开始就不进目录。规则只依赖时间区间和排除区的几何关系，对所有模板和素材库都适用。

## 5. 为什么不用其他方案
- 删掉 `proxy()` 的整窗检查（GLM 诊断的主方案）：那道检查用来防止标题卡、片头片尾混进看片和成片，删掉会放进不该用的画面。
- 只截取窗口里的合格部分去看：会改变 17 秒窗口和 2 秒重叠的拼接规则，牵连连续性分组和边界扩展，改动面太大。

## 6. 怎么验收
新增 `test_catalog_full_window_admission.py`（横跨排除区、但仍有存活记录的窗口不进目录）；服务器全量测试 165 项通过。真实效果要等后续模板的目录页数和运行结果验证。

## 7. 量化数据
目录会少收多少窗口未测量；下次运行时对比扫描日志里的目录总数（原为 1389）。

## 8. 经验与后续
同一个对象的准入判定只能有一个函数，收录和使用两处都调用它。
