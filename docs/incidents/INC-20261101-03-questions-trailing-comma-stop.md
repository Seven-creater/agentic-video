## 1. 问题长什么样
`run_outcome.json`：stage `question_first.parse_json_object`，error `响应中没有完整JSON对象`（src/omni_story/library/question_first.py:96），last_call `glm_003_qfs_questions`。回复完整（finish_reason=stop，1818 completion tokens），只有 casting 数组里多一个尾逗号：`"rough_part":"中段"},],`。

## 2. 怎么查出来的
读任务日志 traceback → 读 calls/glm_003_qfs_questions/response.json 的 content 末尾，找到 `},],`。

## 3. 根因
直接原因：模型输出了不合法 JSON（尾逗号）。根本原因：`parse_json_object` 只做严格解析；直连出题调用没有任何修复路径，一次语法小错就让已付费的分镜和参考理解全部作废。属于容错缺失（代码问题）。

## 4. 解决方案
1. `parse_json_object`：严格解析失败时只做一次机械规范化——删除字符串外、紧接 `}` 或 `]` 之前的逗号；只有结果能作为最外层对象解析才接受；记录 `json_normalisations`。其他语法错误照旧失败。
2. 分镜路径的出题阶段：解析或校验失败时发一次 `qfs_questions_repair1`（新请求，不是重发），附上一份回复和机器可读错误；再失败才 `question_first:questions_invalid`。HTTP 错误不修复、不重发。旧路径不变。

## 5. 为什么不用其他方案
- 通用 JSON 修复库/宽松解析：可能把真正坏掉的回复“修成”错误内容。
- 失败自动重发同一请求：违反不重发规则。

## 6. 怎么验收
新增测试：真实形态 `},],` 解析成功并记录 count=1；字符串内的 `,]` 不动；缺括号仍失败；出题修复 1 次成功/再失败停止/HTTP 错误不修复/恢复零新发送；旧路径不修复。全量测试失败集合等于基线，回放 0 退化，fault_check 关键项为 0。服务器嵌套重跑：12 道题，5 个字母各选不同人物。

## 7. 量化数据
修复前该任务 3 次调用后停机；修复后出题阶段 0 次额外修复即通过（嵌套任务模型重新出题）。

## 8. 经验与后续
模型输出的纯语法小错应由程序在不改变语义的前提下修正并留痕。
