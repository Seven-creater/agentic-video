## 1. 问题长什么样
`model_protocol_repair_exhausted:reference`，仅 3 次调用。attempt 0 `creative_reference_speech_strategy_required`（漏写 strategy，真实内容错误）；attempt 1、2 `Extra data: line 1 column 2138 / 2091`：`..."observed_fact":"男女并肩面向镜头说品牌口号"}]}}}, "uncertainties": [...], "value_judgment": {...}}` —— `]}}` 已回到顶层，第三个 `}` 把最外层对象提前关闭，后面仍是顶层字段。

## 2. 怎么查出来的
读三次 protocol_failure.json 的 model_text，在报错偏移附近查看括号层级。

## 3. 根因
模型偶发的括号错误；`parse_model_json` 只处理尾逗号与游离引号（INC-20261101-03、5ad737b），结构完整的回复因一个字符整份作废。同一参考在之前 4 次运行中都通过，此次是随机触发。属于容错缺失（代码问题）。另：嵌套重跑每次都重新理解参考，增加了这类随机失败的机会（待用户决定是否复用）。

## 4. 解决方案
严格解析和既有规范化都失败后：最外层对象解码完毕、余文以 `, "键":` 开头时，删除那个提前关闭的 `}` 并整体严格重解析；最多 3 次；顶层出现重复键、余文为其他内容或重解析失败一律拒绝；记录 `early_outer_close` 与偏移。

## 5. 为什么不用其他方案
- 通用宽松 JSON 解析：可能把结构错误“修”成错误含义。
- 只靠修复调用：本次两次修复都犯同样的错。

## 6. 怎么验收
两份真实回复恢复全部 10 个顶层字段（偏移 2136、2089），通过创作策略检查与 validate_reference；重复键、`}{"a":1}` 余文仍失败；S8 测试不变。全量测试失败集合等于基线，回放 0 退化，fault_check 关键项为 0。

## 7. 量化数据
修复前 3 次调用 0 份可用；修复后同样回复 2 份可用。

## 8. 经验与后续
同类偶发语法错误可能还有其他形态；每次出现都按“只做确定、可记录的机械修正”原则扩展。
