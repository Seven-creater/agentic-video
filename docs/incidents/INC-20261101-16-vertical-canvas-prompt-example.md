## 1. 问题长什么样
- 用户裁定："需要都是横屏"——创作路线所有交付物必须 1280×720（源片是宽银幕；720×1280 画布只剩中间一条、上下巨大黑边，10-19 已因此抱怨）。
- 实际产出：不烧心 film2 粗剪计划 720×1280，其 final_subtitled.mp4 也是 720×1280；雪山 fix3 粗剪 720×1280。library 模式 theme1 运行"恰好"是 1280×720，并无程序保证。

## 2. 怎么查出来的
- `prompts.plan_prompt` 示例结尾是 `"width":720,"height":1280`（当时 prompts.py:155）；参考片为竖屏时模型照抄示例。
- 沿渲染链确定谁定画布：粗剪渲染调用点（当时 pipeline.py:2340）实际用 `plan['width']/plan['height']`，`functools.partial` 里固定的 WIDTH/HEIGHT 会被调用点关键字覆盖——所以最终画布的真正决定点是**计划本身**；精剪 `story_finecut` 虽固定 1280×720 渲染，但 `parent_layout` 只是从父渲染取裁切 ROI；混流与字幕按 probe 继承输入画布。结论：没有任何一层强制横屏，示例指向竖屏时全链路跟着竖。

## 3. 根因
- 直接原因：提示词示例邀请模型选画布，参考竖屏时模型照抄 720×1280。
- 根本原因：代码问题（提示词与校验不一致/缺程序固定）——画布是硬性交付要求，却交由模型自由字段决定，且全链路"继承"而非"强制"。
- 属设计漏洞而非偶发：library 模式的横屏只是运气（素材恰好横屏），换个竖屏参考即复现。

## 4. 解决方案
- 新任务在输入锁记录 `output_canvas: "1280x720"`（一个共享常量）；`plan_normalisation.py:21`（b1e8f62）`configure_output_canvas` 重启时从 library_state.json 回填该键，锁比较通过。
- `normalise_plan`（plan_normalisation.py:1029，b1e8f62）：带该键时无论模型写什么，每个计划/修订统一 width=1280、height=720，改动即记录 `canvas_landscape_1280x720`；fps 与模型选择的 fit/crop 语义不动。
- 提示词（prompts.py:129/169，b1e8f62）：示例与画布说明在有键时一律 1280×720；无键（旧锁）时还原出与历史逐字节相同的 720×1280 示例。
- 全链路继承：粗剪定初始画布 → 精剪固定 1280×720（parent_layout 只控裁切区域）→ 混流/字幕按 probe 继承；`visual_audio.py:875`（b1e8f62）对非横屏精剪片加硬停兜底 `audio_landscape_canvas_required`。
- 通用性：规则与模板无关，对任何参考片、任何检索模式的新创作任务成立；旧锁与回放门按"无键=旧行为"逐字节不变。

## 5. 为什么不用其他方案
- 只改提示词示例、仍让模型选：无程序保证，换个竖屏参考又回去了。
- 在渲染层强制缩放/裁切成横屏：会改变模型选定的构图语义，且各层已是"继承"关系，在计划归一化层收敛最省、最完备。
- 改写旧任务/旧锁补键：违反录制回放字节不变纪律；旧成片按当时合同处理。

## 8. 经验与后续
- 交付物的硬性几何要求（画布、比例）必须由程序钉死并记录在输入锁里，不能靠提示词示例"建议"；示例本身会被模型当成答案照抄。
- 全链路"继承"型参数要有一个明确的源头层（此处=计划归一化），否则每层都成为潜在分叉点。
- 次要观察（审核者，非缺陷）：visual_audio 的横屏检查先于 sha 检查，改变了新任务的报错优先级；后续若再加画布类兜底，注意报错顺序的可诊断性。
