# INC-20261117-02 挑素材决策的输出被接口内容审核掐断，三次格式修复都失败，找素材停机（02 雪山救狐狸）

| 项 | 内容 |
|---|---|
| 发现日期 | 2026-11-17 |
| 影响范围 | 素材浏览 browser_decide（文本调用，经 opencode）；A、B 两条线共用；致命停机 |
| 状态 | 已修复：A 线 186e814（release 36747a0228fc），B 线 901f58a（release dc97f07256fe） |
| 相关提交 | 186e814、901f58a（仅本地分支，未推送） |
| 相关任务 | `trials/fast_template_20261116_212540_02_雪山救狐狸_01_e5a516763632`（A/B 对比的共用找素材步骤） |

## 1. 问题长什么样
`error: AssertionError:creative_stopped_before_usable_draft:model_protocol_repair_exhausted:material_scene_browser_decide_1`。

三次回复的协议错误：
- 第 1 次（glm_137）：`Invalid control character at: line 1 column 2648`；
- 第 1 次修复（glm_138）：同一个错误；
- 第 2 次修复（glm_139）：`model_response:single_json_object_required`。

回复内容是一段完整 JSON 的开头，后面直接接上了"本代理已达最大步骤数，无法继续执行任务……"这段纯文本。

## 2. 怎么查出来的
1. 看 `agent_events.jsonl`：
   - 第 1 步写到第 2647 个字符时以 `reason: unknown` 结束，token 统计全为 0；
   - opencode 随后进入最后一步（上限 2 步），按系统提示写了"已达最大步骤数"的总结；
   - `text_agent_reply` 把两步的文字用换行拼接，所以报"控制字符"。
2. 排除上下文超限：此前成功的 decide 输入最多 8.8 万 token；而这次输入 13.5 万 token 的总结步骤也正常结束了。
3. 在服务器上把同一个提示词直接发给智谱接口（不经 opencode，不进任务账本）：结束原因 `stop`，完整 JSON 5954 字，思考约 3.2 万 token，用时 552 秒。说明请求本身没问题，模型能完整作答。
4. 对比全部 12 个被截断的步骤（三次调用加修复的续写步骤）：每一个都断在同一组素材的描述上，即野餐组 cg_a844489937a89665（窗口 vl_ada7d5036f100f02、vl_0b21d35cd8c3cd24、vl_e0b4139a4386d2d7），截断前的内容都是"棕发角色持啤酒罐……红晕畅饮……围堵"。
5. 统计全部 626 次历史文本调用：`unknown` 结束的步骤只有这 12 个，外加 1 个空文本步骤（scan_20），之前从未出现过。

## 3. 根因
- 直接原因（推断，证据强）：智谱流式输出的内容审核在模型写到"可爱角色喝啤酒并被围堵"这段描述时掐断了输出。智谱返回的结束原因（如 `sensitive`）不在 ai-sdk 的映射表里，所以被记成 `unknown`。直接调用那次措辞不同，没有触发。
- 根本原因（代码）：
  - 系统没有识别"输出被掐断"，把它当成格式错误去修复；
  - 修复会重发同样的输入，模型会再写同样的内容，在同一处再被掐断。
  - 这和 INC-20261116-09（某个窗口被接口拒绝）是同一类问题：接口对某段素材说不，应该少这一段素材，而不是整个任务停下。

## 4. 解决方案
- `state.py`：新增 `provider_output_cut(events)`。条件是某一步以 `unknown` 结束、已写出内容、后面还有别的步骤，返回被掐断的那段文字。新增 `ProviderOutputCut`（`LibraryStopped` 的子类）。
- `pipeline.py`：
  - 文本调用校验失败时，先查是否被掐断，是则直接抛 `ProviderOutputCut`，不发修复；
  - 续跑复用旧回复的路径做同样的检查。
- `material_browser.py`：decide 捕获 `ProviderOutputCut`，从截断前的文字里取**最后一个完整的** `window_ids` 列表（正在描述的候选），按接口拒绝处理：
  - 移出已看列表，记入 `provider_refused_windows`；
  - 删除包含这些窗口的场景组和粗看结论；
  - 记录 `browser_output_provider_cut`，然后进入下一轮决策。
  - 如果最后一个 `window_ids` 没写完或找不到，就不猜测，照常停机。
- 这套判断不依赖模板、角色或窗口编号，只依赖接口行为和回复结构，对任何参考都成立。A、B 两条线做了相同的改动。

## 5. 为什么不用其他方案
- 放宽 JSON 解析（`strict=False`）或只取第一个对象：截断的 JSON 本来就不完整，解析不出来。
- 多重试几次：12 次截断全在同一处，重试没有用，只是浪费调用。
- 改用别的模型或通道：改动大，也不能保证不被审核拦下。
- 在提示词里要求"不要描述饮酒"：只对这一种内容有效，属于针对个案打补丁。

## 6. 怎么验收
- 新增 `test_provider_output_cut.py`，共 4 项：
  - 截断后接总结步骤的，识别为被掐断；
  - 正常回复、工具步骤、最后一步才截断的，都不算；
  - decide 被掐断后剔除正在描述的窗口，下一轮正常完成；
  - 截断在窗口列表中间时，照常停机。
- 换回旧的 material_browser 后，测试会失败。
- 服务器全量测试：A 线 221 项、B 线 225 项全部通过。
- 用新代码读取服务器上的真实事件日志：三次调用都识别为被掐断，剔除的正是野餐组的 3 个窗口。全部 626 次历史调用里只标记了这 3 次，没有误判。
- 真实续跑：从 212540 续跑，结果待补。

## 7. 量化数据
- 浪费：3 次调用，共 14 个代理步骤（12 个被截断）。从 decide_1 开始到停机约 12 分钟。
- 直接调用对照：完整作答 552 秒，completion 36297 token（其中 reasoning 32302）。

## 8. 经验与后续
- opencode 的 `step_finish.reason=unknown` 应当作为接口异常处理，不能当作模型输出来解析。
- 遗留：只在挑素材的 decide 这一步做了"剔除素材"的处理；别的文本步骤遇到掐断，会以 `provider_output_cut:` 停机（报错清楚，不会无效重试），等遇到时再按各自的输入结构处理。
