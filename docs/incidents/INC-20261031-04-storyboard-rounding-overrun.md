# INC-20261031-04 分镜末格取整超出参考时长被判违规，修复调用遇 HTTP 500 后该模板分镜失败

## 1. 问题长什么样
第一次 7 模板试跑 6 成功 1 失败：雪山参考时长 37.916009 s，模型把最后一格写成 `34–38`，校验报 `storyboard:time_range`；随后的修复调用返回 HTTP 500，按规则不重发，该任务 `failure.json` 停止。

## 2. 怎么查出来的
读试跑 summary 表（雪山 status=failed、attempts=2），再看 response_1.json 的末格时间和 failure.json 的违规码，确认是整数取整导致超出 0.084 s，模型创作内容本身没有问题。

## 3. 根因
校验把"取整到整秒"这种机械误差也交给模型修复（src/omni_story/library/storyboard.py 的时间范围检查，3880068 版）。模型擅长写整秒，参考时长通常不是整秒，这类违规几乎必然出现，每次都多花一次修复调用并暴露在网络错误下。属于校验过严（代码问题）。

## 4. 解决方案
程序机械修正并记录到 `normalisations`（path、before、after、reason）：末格超出时长 ≤0.5 s 截到时长；起点 <0 且 ≤0.5 s 改为 0；相邻格因取整重叠 ≤0.3 s 时把前一格结束改为后一格开始。修正后重新检查格长下限；更大的误差仍报违规给模型。规则只依赖时长和容差常量，对任何参考成立。

## 5. 为什么不用其他方案
- 修复调用失败后自动重发：违反"不重发"规则。
- 要求模型写小数秒：仍会出现取整误差，治标。
- 放宽容差到 1/30 s 以上而不记录：会悄悄掩盖真实越界。

## 6. 怎么验收
新增测试：雪山真实形态（末格 34–38、时长 37.916009）被截到 37.916009 并记录；全量测试失败集合等于基线。第二次 7 模板试跑（trials/storyboard_out_6c940af）全部成功，雪山 1 次调用完成。

## 7. 量化数据
修复前 7 模板 1 个失败、雪山 2 次调用；修复后 0 失败、雪山 1 次调用。

## 8. 经验与后续
数值类机械误差应由程序修正并留痕，修复调用只留给创作内容。
