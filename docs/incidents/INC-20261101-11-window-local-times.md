## 1. 问题长什么样
fix6（release f936f78）停在 `model_protocol_repair_exhausted:plan_0`。第 3 次规划报 `visual_library:range_outside_content`，位置 `$.segments[0].source_in_s`，值 `1.9`（窗口原片范围是 276.5–286.1 秒）。前两次是真实的创作错误：`plan:repeated_source_footage`（两段重叠 3.0 秒）和 seg6 台词缺口 3.22 秒（超出程序可修的 1 秒）。

## 2. 怎么查出来的
对比三次回复的 segments：第 3 次的 12 段时间全部偏小，各段减去的正好是所在窗口的 `source_offset_s`（seg1 278.4→1.9，窗口起点 276.5；seg7、seg8 都减了 2253.5）。请求里窗口观察的 usable_ranges/events 用的是 `local_in_s`/`local_out_s`，并注明 `time_mapping: "source_time_s = source_offset_s + proxy_time_s"`。验证脚本给每段加上偏移：12/12 段都恰好落进唯一一条可用区间，角色也满足。
对照组：fix5 第 3 次（INC-20261101-10）填的是连续的成片时间，加偏移后只有 1/10 段落进区间，属于另一种错误。

## 3. 根因
- 直接原因：模型在最后一次修复里把观察结果的窗口相对时间直接抄进了 source_in_s/out_s。
- 根本原因：提示词里同时出现两套时间域（观察用相对时间，计划要绝对原片时间），要靠模型自己换算；程序对这种可以确定换算的笔误没有容错，反馈也没点明换算公式。
- 类型：容错缺失、反馈不可操作。

## 4. 解决方案
- `src/omni_story/library/plan_normalisation.py`：新增 `_window_local_source_times`，在拆段和台词排窗之前运行。原始时间不在窗口原片范围内、且加上 `source_offset_s` 后恰好落进一条满足角色和 segment_roles 的可用区间时，才换算。整份回复全有或全无：只要有一段换不成，就一段都不改。每段记录 `map_window_local_time_to_source`（原值、新值、偏移），幂等。
- `src/omni_story/library/protocol_feedback.py`：报错还在时，反馈写明"原片秒数 = source_offset_s + 窗口内时间"，给出该窗口的偏移和绝对允许区间。
- 只改 source_in_s/out_s；不改窗口、角色、文本；校验器没有任何改动。这条规则对任何模板、任何电影都成立。

## 5. 为什么不用其他方案
- 在提示词里同时给出绝对时间：会改变所有任务的请求内容，可能影响旧任务续跑，收益又不如程序换算确定。
- 逐段换算（不要求全有或全无）：混合错误时可能把巧合落入区间的段改错，fix5 的反例就是这种情况。
- 推断成片时间轴再反推原片时间：一段成片时间对应多种可能的原片位置，无法确定，所以不做。
