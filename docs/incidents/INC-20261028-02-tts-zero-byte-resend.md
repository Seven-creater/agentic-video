## 1. 问题长什么样
213 次 TTS 调用中 4 次卡死,transport_evidence 签名完全相同:`phase='headers'`、`http_status=None`、`response_bytes=0`、`events=0`、`failure='idle_timeout'`;connected 与 sent 都在约 0.1 秒内完成,随后 60 秒无任何字节。人工补发 3 次全部约 1 秒成功(任务书另记:成功调用整体中位 1.4 秒、最长 4.5 秒)。

## 2. 怎么查出来的
- 排除限流:阿里限流 180 RPM,超限返回 429,不会表现为卡死。
- 空文本免费探测 200 次:200/200 成功、最慢 0.71 秒、4 个 IPv4 都正常。
- 209 次成功调用统计:开始回复用时中位 0.30 秒、最慢 0.64 秒——正常路径远快于 60 秒超时。
- 更早的 curl 实现也出现过同样卡死——与 HTTP 客户端实现无关。
结论:阿里合成后端偶发不接单,不是代码问题。用户起初决定不重发;看到上述证据后批准"仅零字节表头超时签名、每任务最多一次"的自动补发。

## 3. 根因
外部服务问题(阿里 TTS 后端偶发丢弃请求,不发响应也不断连);代码侧的问题是没有区分"这种确定无副作用的可重试签名"与其他结果未知的情况,一律按"未知即停"处理,把可自动恢复的故障变成人工工单。

## 4. 解决方案
- 仅当上一_attempt 签名精确匹配(表头阶段、零响应字节、无 HTTP 状态、idle_timeout)才自动补发一次;其他任何不确定结果(partial body、events>0、total_timeout、连接错误、有 HTTP 状态、curl 时代错误)保持停机。
- 每任务总计最多一次(跨粗剪/精剪/共享缓存/resume):计数先持久化到任务账本再发送;恢复的任务不能再补发。
- 补发前按人工授权路径原样归档原始不确定状态(`original_uncertain.json`),复用既有机器,写自动授权记录(kind `automatic_zero_byte_header_timeout_v1`、`allow_possible_duplicate_charge: true`);不弱化人工授权路径的校验。
- 补发也失败则照旧按未知停机,run_outcome 关联两次尝试。
- 表头阶段 idle 超时降为 20 秒(body idle 与总超时不变);transport_evidence 记录两者。
- 绝不自动重发其他任何调用(Qwen/GLM/其他 TTS 签名)。
通用性:按传输证据签名判定,与文本内容、音色无关。

## 5. 为什么不用其他方案
- 完全不重发(用户最初决定):4/213 的卡死每次都要人工介入;证据表明该签名下服务端零字节响应、补发 3/3 约 1 秒成功;是否已计费无法证实,故自动授权记录写明 `allow_possible_duplicate_charge: true`(最坏多花约 ¥0.003),用户据此改批窄口重发。
- 对一切失败都自动重发:违反"结果未知不重发"的总规则(partial body 等可能已计费);明确排除。
- 缩短所有超时:只缩表头等待(20 秒),body 阶段保持原值,避免误杀慢合成。

## 8. 经验与后续
- "不重发"规则的正确细化单位是传输证据签名:证明请求未到达服务端的签名可安全重发。
- 20 秒表头等待把该故障的暴露时间从 60 秒降到 20 秒。
- 遗留:每任务一次的额度在最坏情况下(两次卡死)仍会停机,按规则接受。
