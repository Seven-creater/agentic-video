# INC-20261102-05 opencode 每次调用往 /tmp 留一个 5.4 MB 的 .so，服务器磁盘写满

| 项 | 内容 |
|---|---|
| 发现日期 | 2026-11-02 |
| 影响范围 | 所有经 opencode 发出的模型调用（视觉调用、文本审核调用），全部路线；运维阻塞，磁盘写满会让正在跑的任务写盘失败 |
| 状态 | 已修复（eb52380，已部署试验环境；真实任务验证待下一条任务） |
| 相关提交 | eb52380 |

## 1. 问题长什么样
用户要求清理服务器磁盘时，`df -h /` 显示 `69G 66G 615M 100%`，当时生产任务 prod_27 正在运行。`/tmp` 占 7.2 GB，其中有 1363 个隐藏文件 `/tmp/.<16位十六进制>-00000000.so`，每个 5,576,816 字节，合计 7.1 GB，最早的 10-24、最新的就是当天，没有任何进程打开它们。

## 2. 怎么查出来的
1. `du` 排查各目录，定位到 /tmp；`ls -a` 发现大量同尺寸的隐藏 .so；`lsof` 确认无进程占用。
2. `readelf`/`strings` 查文件身份：依赖 libc/libpthread，内含 `crates/fff-core/src/background_watcher.rs`，即 opencode 内置的 Rust 文件搜索/监视库。
3. 对照 prod_27 的 `calls/*` 创建时间，.so 的产生时间与每次模型调用一一对应（10:39、10:40、10:42……）。
4. 服务器零成本实验：`opencode --version`、`run --help`、因模型不存在而失败的 `run` 都不解压；用真实 GLM 调用对比：
   - 默认环境：/tmp 新增 1 个；
   - `TMPDIR=<本次调用的 TemporaryDirectory>`：/tmp 新增 0 个，该目录内 1 个，目录随调用结束删除。
5. 代码定位到两个启动点：`src/omni_story/library/opencode_provider.py:320`（视觉调用 Popen）与 `src/omni_story/library/pipeline.py:1406`（文本审核 subprocess.run），都已用每次调用的临时目录做 cwd，但没有设置 TMPDIR。

## 3. 根因
直接原因：bun 编译的 opencode 二进制每次真实运行都把内嵌的原生库解压到系统临时目录，退出时不删除。根本原因：我们启动外部代理进程时只隔离了工作目录，没有隔离临时目录，第三方运行时的临时文件落到全局 /tmp 累积。属于外部组件行为 + 我方容错缺失；与参考模板、电影无关。

## 4. 解决方案
两个启动点在子进程环境里设置 `TMPDIR`、`TMP`、`TEMP` 指向本次调用的 `TemporaryDirectory`（`env` 是本地副本，不影响父进程）。解压出的库随临时目录在调用结束时删除。所有经 opencode 的调用都走这两处，因此对任何任务通用。实现前核对过 opencode 之下的 MCP guard/视觉 MCP 进程：日志、队列、回复都写在任务输出目录，没有需要在 opencode 退出后保留的系统临时文件。环境变量不属于请求哈希，账本与回放不受影响。

当次清理（经用户确认）：删除 10 分钟前的泄漏 .so 7.1 GB；11-01 之前的 54 个旧任务目录约 13.6 GB；bgm-tools/jobs/screen_20261024 3.2 GB；pip 缓存与 systemd 日志约 0.4 GB。

## 5. 为什么不用其他方案
- 定时任务清 /tmp：治标；与运行中的调用有竞态，且要另装 cron 配置。
- 每次调用后按文件名模式删 /tmp/.*.so：依赖 opencode 内部命名，版本一变就失效，还可能误删其他程序的文件。
- 升级/修改 opencode：外部组件，不可控，也不保证上游修复。

## 6. 怎么验收
- 新增 `tests/test_opencode_tmpdir.py`（2 项）：两处启动点的子进程环境 `TMPDIR/TMP/TEMP` 等于子进程 cwd，调用结束后该目录不存在，父进程 `os.environ` 不变。
- 全量 pytest：8 failed / 2595 passed，失败全部在 `out/baseline_2879e5c.txt` 内。
- replay_check：203 行，ok 143 / fixed 21，与 `replay_baseline_98e9427.json` 相比 0 缺失、0 降级。
- fault_check：E1/R1/M1_crash/M2_json/M2_crash 均为 0。
- 服务器机制实验见第 2 节第 4 点。
- 真实任务验证：待下一条用 eb52380 的任务，检查运行前后 /tmp 中 `.*-00000000.so` 数量不变。

## 7. 量化数据
- 泄漏速度：10-24 至 11-02 共 1363 个，约 150 个/天，约 0.8 GB/天。
- 清理前：/ 已用 66 GB，可用 615 MB（100%）；删除泄漏 .so 后可用 7.7 GB（89%）；全部清理后可用 25 GB（64%）。
- 修复后预期每次调用 /tmp 净增 0 个，真实任务实测未测量（见第 6 节）。

## 8. 经验与后续
- 长期跑的服务器应监控磁盘余量（例如余量 < 5 GB 时监控脚本直接报异常）；本次是用户顺手要求清理才发现。
- 遗留：`mcp_http.jsonl` 调用日志单任务可达 100–180 MB（11-01 前的旧任务共 3.5 GB），属于证据账本不能随意删；以后可考虑任务交付后压缩归档。
- 生产命令 omni-server-creative 仍是 d380b0b（未含本修复），切换需用户决定；在切换前生产任务仍会每次调用泄漏一个 .so。
